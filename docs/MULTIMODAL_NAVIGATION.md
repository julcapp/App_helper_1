# Мультимодальная голосовая навигация

Статус: архитектурный контур принят 26.08.2026.

## Цель

Помощник должен сопровождать пользователя до сохранённой безопасной точки не только пешком, но и с использованием общественного транспорта:

`пешком → остановка/станция → транспорт → пересадка → транспорт → выход → пешком`.

Примеры:

`WALK → BUS → WALK → METRO → TRANSFER → METRO → WALK`

`WALK → BUS → WALK → SUBURBAN_TRAIN → WALK`

## Город пользователя: голос сначала, геолокация потом

Для пользователя город сначала уточняется простым голосовым вопросом:

«Уточните город, в котором вы сейчас находитесь.»

Ответ пользователя становится текущим городом профиля и используется для выбора транспортных источников, расписаний, остановок, метро, пригородных поездов и локальных правил маршрутизации.

Геолокация не заменяет этот диалог. Она используется как контрольный сигнал. Если GPS/reverse geocoding показывает, что пользователь переместился в другой город, помощник должен уточнить смену:

«Похоже, вы сейчас в городе Казань. Подтвердить новый город?»

Если город уже встречался в истории пользователя:

«Похоже, вы снова в городе Казань. Использовать этот город для маршрутов и транспорта?»

После подтверждения новый город становится текущим.

## История городов в кабинете пользователя

В профиле хранится текущий подтверждённый город.

Отдельно хранится история посещённых городов:

- название города;
- регион/область, если известны;
- страна;
- дата первого появления;
- дата последнего появления;
- число возвращений в этот город.

История нужна не только для отображения в кабинете. При повторной поездке система может быстрее восстановить знакомый транспортный контекст, ранее сохранённые безопасные точки, предпочтения поездки и локальные настройки.

История не должна автоматически менять текущий город без подтверждения пользователя.

## Пользовательский сценарий

Пользователь говорит: «Отведи меня домой».

Система должна:

1. Проверить текущий подтверждённый город пользователя.
2. Если город ещё не задан — спросить его голосом.
3. Получить текущую позицию.
4. Получить сохранённую точку «Дом».
5. Выбрать транспортный источник, подходящий для подтверждённого города/региона/страны.
6. Запросить актуальный маршрут у транспортного провайдера.
7. Разбить маршрут на последовательные этапы.
8. Озвучивать только ближайшее необходимое действие.
9. Контролировать продвижение по GPS там, где это технически возможно.
10. До посадки явно назвать вид и номер транспорта, если номер передан провайдером.
11. Сразу после выбора транспорта сообщить, сколько остановок нужно проехать.
12. Предупреждать о выходе заранее: за две остановки, за одну остановку и непосредственно на нужной остановке.
13. При отклонении перестраивать маршрут от новой позиции.
14. После выхода из метро/вокзала заново уточнять GPS и продолжать наземное сопровождение.

## Внутренняя модель

`TransitRoute` содержит список `TransitLeg` и подтверждённый `CityContext`.

Поддерживаемые типы этапов:

- WALK;
- BUS;
- TROLLEYBUS;
- TRAM;
- METRO;
- SUBURBAN_TRAIN;
- TRAIN;
- AEROEXPRESS;
- TRANSFER;
- OTHER.

Этап может содержать:

- отдельный номер транспорта (`routeNumber`), например 24, 7, М3;
- отдельное название линии/маршрута (`routeName`), если источник передаёт его отдельно;
- направление движения (`headsign`);
- остановку/станцию посадки;
- остановку/станцию выхода;
- количество остановок;
- время отправления/прибытия, если его передал источник;
- платформу/путь, только если его передал источник;
- расстояние пешего участка;
- дополнительные инструкции провайдера.

Для железнодорожного этапа дополнительно:

- опорный вокзал/станция отправления (`originHubName`);
- конечная станция конкретного рейса (`tripTerminalName`);
- направление движения: «в сторону Москвы», «из Москвы в сторону Тулы», «до Чехова»;
- календарь действия расписания (`ServiceCalendarInfo`);
- дата начала/окончания действия расписания, если их передал провайдер;
- признак, что конкретная дата поездки проверена по календарю перевозчика.

## Электрички и сезонное расписание

Для пригородных поездов нельзя определять расписание просто по правилу «сейчас лето» или «сейчас зима».

Источник маршрута должен проверить фактическую дату поездки по календарю сервиса и исключениям конкретных дней. Если провайдер отдаёт GTFS-подобные данные, для этого используются диапазоны действия сервиса и исключения по датам. Такой подход поддерживает летнее, зимнее, праздничное и временно изменённое расписание без догадок со стороны ассистента.

Если дата поездки подтверждена источником, помощник может сказать:

- «На сегодня действует летнее расписание. Электричка отправляется в 15:42.»
- «По данным перевозчика это расписание действует до 30 сентября.»

Если дата не подтверждена календарём перевозчика:

- «Расписание для этой даты не подтверждено. Я не буду советовать эту электричку, пока не получу актуальные данные.»

## Направление движения электрички

Для электрички одного названия станции назначения недостаточно. Перед посадкой пользователь должен услышать понятную ориентацию:

- «Вам нужна электричка в сторону Москвы.»
- «Вам нужна электричка из Москвы в сторону Тулы.»
- «Садитесь на электричку по направлению Чехов.»
- «Отправление с Курского вокзала. Вам нужна электричка до Чехова.»

Если пользователь находится не на начальном вокзале, помощник должен назвать текущую станцию посадки и направление конечной/опорной станции.

Если маршрут начинается с вокзала без промежуточной наземной станции, вокзал выступает опорной точкой маршрута.

## Комбинированный сценарий автобус → электричка

Пример штатного маршрута:

1. «Дойдите до остановки “Центральная”.»
2. «Дождитесь автобуса номер 24 в направлении вокзала.»
3. «Проедьте четыре остановки. Я предупрежу заранее.»
4. «Выходите на остановке “Станция”.»
5. «Пройдите ко входу на железнодорожную станцию.»
6. «Вам нужна электричка по направлению Чехов.»
7. «Отправление в 15:42. Платформа 3 — только если это подтверждено текущими данными перевозчика.»
8. «Проедьте семь остановок и выйдите на нужной станции. Я предупрежу заранее.»

## Правило достоверности

Помощник не имеет права самостоятельно придумывать:

- текущий город пользователя;
- номер автобуса, троллейбуса, трамвая или другого маршрута;
- номер платформы или путь;
- номер выхода метро;
- фактическое расписание;
- сезон расписания;
- направление конкретного рейса;
- конечную станцию рейса;
- остановки конкретного маршрута;
- факт задержки/отмены транспорта.

Город считается текущим только после голосового/интерфейсного подтверждения пользователя. Геолокация может предложить смену города, но не должна молча менять его.

Остальные транспортные сведения произносятся только при наличии в ответе реального транспортного источника.

Если платформа не передана источником, помощник должен сказать:

«Платформа в данных маршрута не указана. Проверьте табло или указатели на станции.»

## Голосовое сопровождение

Основной UX: один шаг — одно действие.

Перед посадкой помощник должен назвать транспорт максимально однозначно:

- «Дождитесь автобуса номер 24 в направлении “Вокзал”. Садитесь на остановке “Центральная”.»
- «Дождитесь троллейбуса номер 7. Нужно проехать 6 остановок.»
- «Вам нужна электричка по направлению Чехов. Отправление с Курского вокзала.»

После посадки помощник сообщает весь необходимый запас до выхода:

- «Нужно проехать пять остановок. Я предупрежу заранее.»

Далее срабатывает ступенчатое предупреждение:

1. за две остановки: «Через две остановки нужно выходить на “Площадь”.»;
2. за одну остановку: «Следующая остановка — ваша: “Площадь”. Приготовьтесь выходить.»;
3. на нужной остановке: «Выходите на остановке “Площадь”.».

Для электрички используются те же предупреждения, но с термином «станция».

Каждое такое предупреждение должно произноситься один раз для текущего транспортного этапа.

## Метро и подземные переходы

GPS внутри метро, тоннелей, подземных переходов и крупных вокзалов может быть недоступен или неточен.

Поэтому внутри таких зон навигация должна опираться на структуру маршрута от транспортного провайдера, известные станции и пересадки, голосовые контрольные точки и повторное определение позиции после выхода на поверхность.

## Отклонение от маршрута

При существенном отклонении от ожидаемого пешего участка:

«Похоже, вы отклонились от маршрута. Перестроить маршрут от текущего места?»

Если пользователь вышел из метро через другой выход, система должна по возможности перестроить следующий наземный участок, а не автоматически заставлять возвращаться к первоначальному выходу.

## Транспортные провайдеры

Архитектура провайдер-независимая через `TransitRouteProvider`.

Выбор провайдера выполняется после определения подтверждённого города/региона/страны.

Планируются адаптеры:

- 2GIS — приоритетный транспортный адаптер для поддерживаемых регионов России;
- Google Routes Transit — международный/резервный адаптер для поддерживаемых стран;
- отдельный железнодорожный источник/адаптер для актуального расписания пригородных поездов, если общий провайдер не предоставляет достаточной точности;
- в будущем другие локальные провайдеры могут подключаться без изменения голосового ядра.

На текущем этапе реальные HTTP-вызовы не добавляются до получения и безопасной настройки API-ключей.

## Следующие технические этапы

1. Связать голосовой вопрос о городе с первым запуском/первым запросом навигации.
2. Связать reverse geocoding с `CityContextManager` только как сигнал возможной смены города.
3. Показывать текущий город и историю посещённых городов в кабинете пользователя.
4. Подключить первый реальный `TransitRouteProvider`.
5. Проверить покрытие пригородных железнодорожных расписаний и исключений конкретных дат.
6. При необходимости подключить отдельный железнодорожный адаптер.
7. Связать `TransitNavigationSession` с фактическим прогрессом по остановкам/станциям.
8. Подключить `TransitRideAlertTracker`.
9. Реализовать контроль отклонения и перестроение.
10. Добавить режим «Я заблудился» с предложением маршрута домой и связи с доверенным контактом.
